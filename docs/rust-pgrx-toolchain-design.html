DECISION

把变化收敛在工具链层

官方构建以 Rust 1.100.0 / pgrx 0.20.0 为目标基线。普通配方保留标准命令；环境准备负责装包、设置默认版本和检查真实命令。旧 pgrx 仅作为过渡版本槽保留。

软件包安装成为默认

pgext env rust/pgrx 默认走 APT/DNF。找不到指定包时明确失败，不隐式退回联网编译。rustup 作为明确选择的独立环境模式。

标准命令保持不变

通过 /usr/bin 提供 Cargo、Rust 和 pgrx 入口。即使配方重置为常规系统 PATH，也能找到工具。

默认统一，任务可固定

系统默认 pgrx 为 0.20.0；任务启动时固定版本与 PGRX_HOME。并发任务不修改系统默认值。

工具要求独立于发行版包名

移除扩展配方对发行版 rust/cargo/rustc/rustfmt 的错误约束；保留实际工具检查与其他真实构建依赖。

本轮更新

目标载荷已经进入公网索引。 2026-11-21 16:51（北京时间），repo.pigsty.cc 与 repo.pigsty.io 的 APT/YUM、两架构八路索引均出现 Rust 1.100.0 和 pgrx 0.20.0。此前会话中的“尚未公开”状态已被这次读取结果取代。此次为索引读取，未重复执行公网整仓签名验收。S7

当前 pgext 仍以 rustup 安装 Rust、以 cargo install 安装 pgrx，默认 0.19.3；代码硬编码用户 Cargo 路径。现有 Rust 包只提供私有前缀，尚不拥有标准命令。S1S2

PACKAGE MODEL

两个入口包，一个基线元包

建议新增三个轻量包。两个入口包提供真实文件；一个元包聚合并锁定版本。元包不是伪造发行版能力名：不使用 Provides: cargo/rust 让不正确的依赖检查“通过”。

依赖精度：区分包版本、工具版本与构建批次

Rust/pgrx 自身的版本保持上游语义；入口包用自己的接口版本（例如 1.0.0-1PGSTY）；元包用经过验收的基线版本（例如 2026.11.21-1PGSTY）。以下是依赖设计示例，不是已发布包：

cargo-pgrx-default (= 1.0.0-1PGSTY)
rust-toolchain (= 1.100.0-1PGSTY)

# RPM 使用相同的精确 EVR 关系，采用原生 RPM 比较语义。
# 未来重打包提升 release，必须发布并验证新的基线组合。

精确依赖只能防止组合漂移，不能代替制品保存。仓库清理旧版本前，必须在独立基线归档中保留 RPM/DEB、SHA256 和镜像摘要；回退不能依赖一个已经被剪枝的旧包。

需要一起落地的规则

当前 infra-pkg/bin/lint_specs.py 禁止 conflicts/provides/replaces/obsoletes。应只为 rust-toolchain-default 的经核实文件冲突增加包名 + 格式 + 字段 + 值级别白名单，并补回归检查。不要全局取消限制，也不要用 Replaces/Obsoletes 接管发行版载荷。实际冲突包名要通过各发行版包文件清单确认。S4

FILESYSTEM & PATH

系统程序与用户状态各归其位

继续使用已有私有运行时目录，避免搬动经过验证的载荷。公共链接由入口包拥有；默认目标由系统 alternatives 管理；编译缓存和 PG 注册信息不写入系统程序目录。

路径所有者 / 用途
/usr/lib/pgsty/rust/Rust 载荷包 · 当前单一 Rust 工具链；程序与目标标准库保持同一版本。
/usr/lib/pgsty/cargo-pgrx/X.Y.Z/bin/cargo-pgrxpgrx 版本槽 · 实际 ELF；多个版本之间无文件覆盖。

# PostgreSQL 目录由实际平台与本次 PG major 决定。
<PG bin>:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

# Rust / pgrx 的正式入口位于 /usr/bin。
# 每次构建预检 PATH 与 CARGO_HOME，确认它们没有被其他程序遮蔽。

不把新文件放进 /usr/local 或用户的 ~/.cargo/bin。 前者留给本机管理员，后者是用户工具空间。只放一个 /etc/profile.d 脚本也不够：非登录 shell 不一定加载它，现有配方还可能重置 PATH。

旧 rustup 环境怎么迁移，而不损坏用户数据？
  1. 优先重新构建干净镜像或使用独立构建账户。开发账户里的 rustup 可以继续服务其他项目。
  2. 原地迁移前记录系统包所有者、command -v、最终链接目标和版本；对旧命令入口做可恢复备份，只处理本次相关 Rust/pgrx 入口。
  3. 保留需要的 registry/git 缓存、Cargo 配置和认证。不要整树删除 ~/.cargo、~/.rustup。
  4. 旧配方即使把 $HOME/.cargo/bin 放到 PATH 前面，只要里面没有冲突工具，仍可正常找到系统入口。存在冲突时预检失败，不能宣称只改 PATH 已解决。
  5. 若使用独立 CARGO_HOME，显式迁移必要镜像配置；认证只按原权限与需要配置，不写进镜像或报告。
VERSION SELECTION

一个默认值，明确的任务覆盖

pgrx 版本选择顺序固定为：任务指定版本 → 系统手动默认 → 报错。不扫描目录挑“最新版”，不在构建中安装缺失版本，不切换全局默认以服务某个临时任务。

使用固定基线

普通配方无需理解版本槽

系统默认在环境准备阶段设为 0.20.0。正式任务仍显式固定版本与 PGRX_HOME，防止其他管理员操作改变构建选择。

PGEXT_PGRX_VERSION=0.20.0 \
PGRX_HOME=/work/job-a/pgrx/0.20.0/pg18 \
cargo pgrx --version
这里展示拟议接口。PGEXT_PGRX_VERSION 已用于本轮包装器原型，尚不是正式 pgext 的已发布参数。

系统默认：原生 alternatives

管理的是私有链接 /usr/lib/pgsty/cargo-pgrx/default。公共 /usr/bin/cargo-pgrx 始终是同一个包装器，由它找到实际 ELF。

安装版本槽与激活默认值分开。pgext env pgrx --pgrx 0.20.0 在准备阶段注册指定槽并选择手动模式；构建阶段不调用 alternatives。

单次任务：环境变量固定

包装器严格验证 PGEXT_PGRX_VERSION=X.Y.Z，只在已安装的固定前缀中查找。选择后设置同一套 CARGO/RUSTC/RUSTDOC/RUSTFMT。

每个任务单独初始化 PGRX_HOME；初始化与打包必须继承同一选择。显式旧版命令 cargo-pgrx-0193 继续保留。

为什么不能只给现有包装器加一个软链接？

Cargo 调用插件时会把 pgrx 作为参数传入。现有 cargo-pgrx-0200 包装器又主动补一次 pgrx。直接把它链接成 cargo-pgrx 会得到重复参数；本轮在两平台上均复现了这个错误。S3

新通用包装器先规范化这个参数，再调用私有目录中的真实 ELF。这样 cargo pgrx --version 和 cargo-pgrx --version 都成立，而旧显式版本入口不必马上改变。

Rust 多版本：第一阶段保留简单模型

现有 rust-toolchain 是单一包名、单一前缀，升级替换旧版。同一个包名不能据此宣称多版本并存。 当前建议以镜像固定不同 Rust 基线，在同一个正式镜像中只保留一个受控版本。

将来确有同机多 Rust 需求，再拆成 rust-toolchain-1.100.0 等不同包名，安装到 /usr/lib/pgsty/rust/1.100.0/；把 Cargo、rustc、rustdoc、rustfmt 与标准库作为一组切换。届时必须同步修改 pgrx 包装器固定的 Rust 路径。不要先创建一个 current 链接，就声称现有包已经支持共存。

BUILD CONTRACT

去掉错误包依赖，补上真实能力检查

扩展配方声明所需能力，环境准备负责满足它。用户通过 rustup 安装的编译器，不会在 RPM/dpkg 数据库中表现为发行版的 rust/cargo；检查某个包名无法证明实际执行的是那个编译器。

处理范围新契约
移除扩展配方中错误的发行版 Rust/Cargo/rustfmt 构建依赖环境已准备好工具链；实际命令与版本由构建预检验证。
保留PG 开发文件、C/C++ 编译器、clang/libclang、真实链接库、打包工具继续由 APT/DNF 和原生打包检查验证。
保留Rust/pgrx 工具包自身的真实运行依赖例如 libc、libgcc、tar/gzip，以及版本槽实际使用的私有 Rust。
补强实际工具链、Cargo 配置与来源记录预检最终路径、版本、sysroot、PGRX_HOME、LLVM、PG 配置及锁文件；构建结果记录这些值。

需要对依赖字段做一次集中、窄范围整理。 这不是把配方重写成另一套调用方式。保留原有 cargo pgrx 构建逻辑，不使用批量 --nodeps / -d 跳过所有检查，也不在 pgext 中用正则临时删掉任意依赖表达式。已有绕过检查的配方，应在工具依赖整理后逐步恢复原生检查。S1

正式预检要覆盖的内容

  • 入口与供应方检查命令最终路径、链接与包所有者，检测 /usr/local/bin、用户 rustup proxy 和 $CARGO_HOME/bin/cargo-pgrx 的遮蔽；包模式不能混入另一套编译器。
  • 版本与组件读取 rustc -vV、Cargo/pgrx 版本和 Rust sysroot；核对源代码的 MSRV、rust-toolchain.toml、精确版本检查及必要 target。普通 Cargo 不会替 rustup 解释工具链文件。
  • pgrx 与 PG源代码及 Cargo.lock 的 pgrx 系列依赖与 CLI 对齐；检查实际 pg_config、开发头文件和目标架构，显式注册本次 PG major，使用 --no-run。
  • LLVM 与本机构建pgrx 0.20.0 要求匹配 major 的 clang/libclang，优先同版本 llvm-ar，并需要宿主 C 编译器；Rust 至少 1.99.1。本方案第一阶段按各平台原生架构构建，不默认引入交叉编译。S6
  • 复现与并发记录完整包版本、SHA256、镜像摘要、源码及锁文件摘要；每任务独立 PGRX_HOME 和构建输出。共享下载缓存可以保留，编译期间不升级工具链或修改全局默认。

PG13 / PG14 遗留0.20.0 已移除这两代支持。同步 features、初始化参数与测试范围；全局活跃策略是 PG15–19，EL8/PG19 为 N/A。

MIGRATION & OPERATIONS

分阶段接入，保留可用的旧基线

先证明包与入口正确，再迁移扩展源码和配方。0.20.0 的新镜像可以先行准备；在扩展完成适配前，旧版本构建仍使用原来的固定镜像。

1

落地三个新包

实现 Rust 标准链接、pgrx 通用包装器、有限 alternatives 生命周期与精确基线元包。为唯一需要的冲突关系添加 lint 白名单，补充文档。

退出条件：RPM/DEB 的安装、升级、卸载、冲突检测及两架构解析通过。
2

接入 pgext 环境与构建预检

移除用户 Cargo 路径硬编码；包安装为默认，rustup 模式显式选择。环境准备负责安装与激活；每任务固定版本、PGRX_HOME 和实际 Rust 路径；plan 输出须准确展示这些动作。

退出条件：新旧来源不会被混用，版本缺失和遮蔽能在编译前失败。
3

建立 0.20.0 候选镜像

更新 Dockerfile 与共享 pgext.mk；去掉 rustup 和 cargo-install 初始化路径，安装固定元包。保留旧镜像的不可变摘要；候选镜像先使用独立标签。

退出条件：两种包格式与架构代表环境跑通，再覆盖 16 个构建平台。
4

统一扩展依赖和必要配方字段

逐批更新 pgrx 源码/锁文件，清理发行版 Rust 依赖、旧 PG 参数及特殊 target 准备。对一般扩展保留原有构建命令，记录少数例外。

退出条件：按扩展实际支持范围通过编译、打包、CREATE EXTENSION / 升级与核心功能测试。
5

发布基线并切换正式构建

完成包签名与索引验收、发布固定镜像及来源清单，再把正式构建指向新基线。归档旧载荷与镜像；发生失败时切回已验收的旧组合。

退出条件：公开安装链路和构建产物验证完成；来源安装、代码部署、包发布分别记账。
包生命周期：安装、升级和卸载如何处理？
动作约定
安装载荷槽只增加自己的文件。已有槽保持不变。单独装槽不意味着进入官方构建基线。
安装入口包标准文件由包管理器拥有；检测文件所有权冲突。pgrx postinstall 在载荷存在后注册默认候选，保留已有手动选择。
激活默认pgext env pgrx 明确设置手动默认。元包只聚合依赖，不在安装脚本中切换版本。首次无默认可由原生工具建立候选默认，正式构建仍须预检并固定。
增添历史槽显式版本命令或任务覆盖可直接使用。需要作为系统候选时，由环境准备注册；不必立即重打包所有旧槽。
入口包升级包装器应向后兼容，保留管理员选择。区分 Debian 的 upgrade/remove/purge 和 RPM 脚本参数，不能在升级中误删 alternatives 组。
卸载某版本注销对应候选；对未配套 hook 的旧槽，卸载前由环境管理流程注销。预检要识别失效链接。元包依赖应阻止意外移除基线；本机 alternatives 的回退不等于允许构建降级。
卸载入口包移除入口与其拥有的注册，保留版本槽、用户配置和缓存。重复执行脚本必须幂等。

不能直接覆盖或手工写入 alternatives 状态数据库。实现阶段应测试两种系统管理器真实行为，包括卸载当前选择、重装和中断后恢复；原型中的“移除候选”测试尚不等于这些包事务已通过。
